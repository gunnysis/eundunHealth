## 1. 배경 및 사용자 가치 (Problem & Value)

### 사용자가 겪는 문제 (User Problem)
- 현재 eundunHealth는 주 7일 중 **오직 1개 요일(Int 1~7)만 휴식일로 지정**하도록 강제되어 있다 (`val restDay: Int = 7`).
- 이는 시스템적으로 **주 6일 고강도 운동을 강제**하는 구조이다.
- 보디빌더 수준의 주 6일 운동은 은둔헬스의 주요 타깃 페르소나(운동을 다시 시작하는 초보자, 홈트레이닝족, 바쁜 직장인/학생)에게 지나치게 가혹하며, 3~4일만 운동해도 "이번 주 계획 완주에 실패했다"는 패배감을 유발하여 **앱 이탈(Churn)의 가장 큰 심리적 요인**이 된다.
- WHO, ACSM(미국스포츠의학회)의 권고(주 150분 중강도 운동, 주 3~5일 운동)와도 괴리가 있으며, 충분한 회복 없이 오버트레이닝이나 관절 부상 위험을 초래할 수 있다.

### 제공할 사용자 가치 (User Value)
1. **작은 성공의 누적 (Small Wins)과 자기효능감**:
   - 사용자가 본인의 체력과 스케줄에 맞춰 "화·목·토·일 휴식(주 3일 운동)"을 스스로 정하고 3일을 채우면, **"이번 주 목표 100% 완주!"**라는 강력한 성취감을 제공한다.
2. **라이프스타일 적합성 (User Autonomy)**:
   - 주말(토, 일) 완전 휴식을 원하는 직장인, 격일(월/수/금) 운동을 원하는 초보자 등 다양한 생활 패턴에 앱이 자연스럽게 맞춰진다.
3. **지속 가능한 리텐션(Retention)**:
   - 포기하지 않고 장기적으로 운동 습관을 유지할 수 있는 심리적 완충지대를 제공한다.

## 2. 핵심 콘셉트 및 UX 인터랙션 (Concept & UX)

### 핵심 아이디어 (Core Idea)
> **"사용자는 요일 칩으로 자유롭게 휴식일을 선택하고, 시스템은 남은 실제 운동 일수($N$)에 맞춰 최적의 분할 루틴(전신 ➔ 상/하체 ➔ 3분할)을 스마트하게 자동 리모델링한다."**

### 화면 흐름 및 인터랙션 (User Flow)
- **Profile / 온보딩 화면**:
  1. **상단 빠른 추천 프리셋 (Quick Presets)**:
     - `[초보자: 주 3일 (격일 운동)]` ➔ 화, 목, 토, 일 자동 선택
     - `[직장인: 주 5일 (주말 휴식)]` ➔ 토, 일 자동 선택
     - `[하드워커: 주 6일 (현행)]` ➔ 일요일만 선택
  2. **하단 요일별 멀티 토글 (월 ~ 일 FilterChips)**:
     - 사용자가 원하는 요일을 자유롭게 탭하여 `휴식` 상태를 켜고 끈다.
     - 선택에 따라 상단 뱃지에 *"이번 주는 주 4일 운동 루틴이 생성됩니다"* 같은 직관적인 안내를 표시한다.

### 안전장치 및 가드레일 (Guardrails)
- **운동일 최소 보장 (1일 ~ 6일)**:
  - 7개 요일을 모두 휴식으로 선택하려 할 경우: *"최소 1일 이상은 운동일이어야 계획을 생성할 수 있어요"* 토스트 안내 후 마지막 1개는 토글 불가 처리.
- **연속 휴식 안내**:
  - 4일 이상 연속 운동이나 4일 이상 연속 휴식 시, 가벼운 건강 조언 넛지 제공.

## 3. 기술 아키텍처 밑그림 (Technical Architecture)

### 3.1 데이터 모델 및 API 계약 (Data & API Contract)
- **단일 정수 ➔ 정수 배열(`List<Int>`)로 확장**:
  ```json
  // PUT /v2/profile/rest-days 또는 ProfileRequest
  {
    "heightCm": 175.0,
    "weightKg": 70.0,
    "restDays": [2, 4, 6, 7]  // 화(2), 목(4), 토(6), 일(7) 휴식 (ISO-8601 요일 1=월 ~ 7=일)
  }
  ```
- **PostgreSQL**: `user_profiles.rest_days INTEGER[] DEFAULT '{7}'` 또는 `JSONB` 컬럼.
- **Android Room**: `TypeConverter`를 통한 `List<Int>` ⇄ `String` 변환.

### 3.2 핵심 비즈니스 로직: 동적 적응형 분할 엔진 (Adaptive Split Engine)
사용자가 지정한 실제 운동 일수 $N = 7 - restDays.size$에 따라 루틴의 분할 방식을 동적으로 결정한다.

| 운동 일수 ($N$) | 분할 전략 (Routine Strategy) | 부위별 슬롯 구성 |
| :---: | :--- | :--- |
| **주 1~2일** | **전신 고효율 복합 (Full Body)** | 하루에 상체·하체·코어를 고루 다루는 전신 풀바디 복합 A/B 루틴 |
| **주 3일**<br>*(골든 루틴)* | **전통 3분할 (Push / Pull / Legs)**<br>또는 **전신 A / 전신 B / 유산소** | • Day 1: 가슴/삼두/코어 (Push)<br>• Day 2: 등/이두/후면 (Pull)<br>• Day 3: 하체/둔근/유산소 (Legs) |
| **주 4일** | **상체 / 하체 2분할 (Upper / Lower)** | • 상체 A ➔ 하체 A ➔ 상체 B ➔ 하체 B |
| **주 5일** | **부위별 4분할 + 전신 유산소** | • 가슴 ➔ 등 ➔ 하체 ➔ 어깨/코어 ➔ 전신 유산소/피니셔 |
| **주 6일** | **3분할 2회전 (현행 시스템)** | • Push ➔ Cardio ➔ Pull ➔ Cardio ➔ Legs ➔ Mixed |

#### 알고리즘 동작 흐름 (`AdaptiveWeeklyPlanGenerator`):
```text
1. 전체 7일 중 restDays에 속하지 않는 날짜 목록(List<LocalDate>) 추출 (크기 N)
2. N에 해당하는 RoutineStrategy 선택 (전신, 2분할, 3분할 등)
3. seed = weekStart.toEpochDay() 기반 결정론적 셔플로 N개의 Exercise 슬롯 생성
4. 7일 캘린더 순회:
   - if (date.dayOfWeek in restDays) -> DayPlan(isRestDay = true, emptyList())
   - else -> DayPlan(isRestDay = false, slot = slots[slotIndex++])
```

### 3.3 타 시스템 영향도 (Cross-system Impact)
1. **식단 AI (DeepSeek MaaS)**:
   - 프롬프트에 `restDays: ["화요일", "목요일", "토요일", "일요일"]` 목록을 전달하여, 운동일에는 고단백 식단을, 휴식일에는 칼로리를 조절한 가벼운 회복식을 맞춤형으로 생성.
2. **진행 통계 및 뱃지**:
   - 주간 목표 달성률 분모를 고정 6일이 아닌 사용자의 실제 운동 일수($N$)로 계산 (`3/3일 완료 = 100%`).
   - "주 3일 목표 완주" 등 목표 기반 성취감 부여.
3. **Health Connect 동기화**:
   - `!it.isRestDay`인 날에만 자동 체크하는 기존 수동 우선 로직이 $N$일에 맞춰 투명하게 동작.
